Age-0/age-1 optimistic RYW escalation vs baseline -- urcu-txn 3-hash (POSITIVE half)
2x96-core EPYC (384 hwthreads), jemalloc, --ryw 1, best-of-3 @ 800 ms.
ALL curves on the CURRENT engine: the spinlatch install (-DURCU_MCAS_NO_HELP
-DURCU_MCAS_NO_STEAL), decide/settle CAS -> release store.

THE WORKLOAD (disjoint)
  --nbuckets 16384 --updatespacing 512 --movesper 8, RYW FORCED ON (--ryw 1).
  8 consecutive keys hit 8 DISTINCT buckets (chunk 8 < nbuckets 16384), so a
  commit's write-set is disjoint and genuine read-your-own-writes is ~0.  RYW is
  forced on so the escalation path is exercised; every escalation is therefore a
  Bloom FALSE POSITIVE, not a real coincidence.  This is the mirror image of the
  batched 3-skiplist (adjacency-forced ~100% genuine RYW) and the same regime as
  the SPARSE 3-skiplist -- see age_escalate_skiplist.

THE SCHEME
  Age 0 (retry==0): skip the write-set find on BOTH the load and the store path,
  skip the record sort, and install with a try-latch (fail fast on a foreign
  proxy).  A Bloom coincidence sets esc_pending -> commit ABORTS -> re-run at age
  1+ (Bloom+find+sort).  On a disjoint write-set with a good filter, age 0 almost
  never escalates, so it reaches install and pays none of the sort, the find, or
  the blocking install.
    The store-path find skip is the age-0 BLIND APPEND, now folded into
  AGE_ESCALATE: at age 0 esc_pending already discards any same-slot coincidence
  before install, so the reconcile find (an O(nr) write-set scan run on every
  store) is redundant and the store just appends.  Profiling showed that scan was
  the single largest age-0 self-time chunk (~19.5% at 32 cores, ~17% at 192) and
  it is contention-independent, so removing it lifts the whole curve -- see below.
  Flags: -DURCU_TXN_AGE_ESCALATE -DURCU_MCAS_AGE0_TRYLATCH; filter -DURCU_TXN_BLOOM_K
  x -DURCU_TXN_BLOOM_WORDS.  esc-dumb = 64-bit k=1; esc-smart = 1024-bit k=3.

     at 64-192.  The blind append removed a contention-independent O(nr) write-set
     scan (the reconcile find) that was the dominant age-0 self-time, so the win

  -> esc-dumb LOSES 0.84-0.91x EVERYWHERE.  The k=1 64-bit filter false-positives
     on contiguous calloc'd bucket-head addresses (~all commits collide in one
     word), so it escalates almost everything -- the filter, not the mechanism, is
     what sinks it.  The good filter is load-bearing.

WHY IT WINS HERE AND NOT ON THE BATCHED SKIPLIST
  The only precondition age 0 needs is a DISJOINT write-set so it reaches install
  without hitting a genuine coincidence.  The hash (and the sparse skiplist)
  provide it; the batched skiplist (adjacency) does not, so there age 0 pre-aborts
  and loses.  Given disjointness, the win is bounded by (a) the filter quality
  (k=1 escalates on FPs -> loses; k=3 -> wins) and (b) contention (install
  collisions at high core counts reintroduce escalation) -- but the find skip is
  paid back regardless of contention, which is why the high-core win no longer
  erodes to parity.

CORRECTNESS
  bench conservation check passes at every core count / filter (95040 owned keys
  accounted for, 100% reader hit).  The disjoint workload never aliases a bucket,
  so RYW is not needed for correctness here (--ryw 1 is forced only to exercise
  the escalation path).  The blind append is safe because esc_pending discards any
  same-slot descriptor before it is ever installed.
