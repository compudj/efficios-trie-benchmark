DLM+SW dentry cache -- per-host CHAIN LOCK vs the mixed SW/MW commit
===================================================================
2×96 EPYC 9654, one hw thread/core (0..191), jemalloc, best-of-5, conservation-
gated.  dirs decontended to 16/writer (so the ONLY writer contention is the
transition chain, not the index buckets).  data: scripts/dcache_swmw.csv;
figure: figures/dcache_swmw.png; sweep: scripts/run_dcache_swmw.sh.

Three arms -- identical reader + mark; only the chain (d_fwd/d_back) differs:
  dlm           default: index SW (bucket-locked) + per-host CHAIN LOCK.  176 B.
  dlm-swmw      -DDC_CHAIN_SWMW: chain rides the mixed commit as MW records
                (CAS-old serializes adjacent folds); chain lock RETIRED.  168 B.
  dlm-swmw-pad  -DDC_CHAIN_SWMW -DDC_SWMW_PAD: mixed engine + 8 B dead padding
                -> 176 B, the SAME-SIZE control.

CONCLUSIONS
-----------
1. The win is the lock-free CHAIN, not the -8B footprint.  dlm-swmw (168 B) and
   dlm-swmw-pad (176 B) track each other within noise across every panel, so the
   speedup is the MECHANISM (retiring the per-host chain lock that serialized
   every stack demote and every fold of a chain), not cache density.  On this
   allocator a 64-aligned 168 B and 176 B object both occupy 3 cachelines, so the
   -8B is a real footprint saving but a throughput no-op here.

2. It is a genuine TRADE-OFF with a crossover at ~4 threads.  The mixed commit's
   descriptor machinery (install/decide/settle + call_rcu the descriptor) makes a
   rename ~1.6x MORE EXPENSIVE uncontended, so the chain-lock build wins 1-2
   threads.  Past the crossover the lock-free chain scales where the chain lock
   serializes: swmw is ~1.9x at 8-16 threads, ~3x at 32-64, and 3.5x (and still
   climbing) at 192, where dlm has plateaued near 14 Mrenames/s.  Correcting an
   earlier fixed-dir spot-check that read as a flat "1.8-2x": with dirs
   decontended (chain isolated) the honest shape is crossover + widening win.

3. The fair-mutex escalation lane the mixed front-end reintroduces does NOT cost
   the shell ops at scale -- swmw keeps scaling cleanly to 192 threads with no
   collapse.

4. Reads are untouched when uncontended (frac=0: wash).  Under HEAVY concurrent
   rename load the swmw readers run ~12-18% slower than the chain-lock readers
   (the MW commit's higher reclaim/descriptor traffic on the shared machine),
   offset by ~3x the write throughput -- a writer-throughput-for-reader-tax trade
   worth stating, not a reader-path regression (the reader code is identical).
