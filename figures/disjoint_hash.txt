Disjoint-write-set hint -- Bloom-free age-0 blind append -- urcu-txn 3-hash
2x96-core EPYC (384 hwthreads), jemalloc, spinlatch, median-of-5 @ 800 ms.
Engine: userspace-rcu-txn urcu_txn_declare_disjoint().  Resswept after the
invisible-writes mode was retired: read-your-own-writes is now the unconditional
default, so the old ryw-off "find" baseline (a reconcile find on every store) is
gone and two curves remain.

THE HINT
  The age-0 blind append -- skip the O(nr) reconcile find on every store -- is the
  fast store path, and BOTH curves here take it.  Read-your-own-writes (the
  engine's default) makes it safe on a general write set: its Bloom test_and_set
  flags a same-slot coincidence with esc_pending, so commit discards the
  descriptor before install.  A mutator whose write set is DISJOINT by
  construction -- a hash add/remove over distinct buckets -- has no coincidence to
  catch, yet still pays the whole filter (per-store hash-and-set, per-load test,
  128 bytes to zero per attempt).  urcu_txn_declare_disjoint() lets the handle
  assert the guarantee and drop the filter entirely: the store gate is retry==0
  unconditional, and the Bloom is maintained only when !disjoint.  So disj and the
  default differ ONLY by the Bloom -- this measures the filter's cost in
  isolation.  Contract is the caller's -- a store onto a recorded slot corrupts
  (dup record); -DURCU_TXN_DEBUG_DISJOINT traps it (find != NULL -> abort).

THE WORKLOAD (disjoint)
  --nbuckets 16384 --updatespacing 512 --movesper 8.  8 consecutive keys hit 8
  DISTINCT buckets (chunk 8 < nbuckets 16384), so a commit's write set is
  disjoint and genuine read-your-own-writes is ~0.  Measured directly: 0 true
  WAW over 18.4M commits (vs 5.36M on an aliasing control) -- the Bloom never
  resolves anything here; every escalation it drives is a false positive.

TWO CURVES (one binary; only the runtime flag differs, so there is no code-layout
confound)
  disj : --disjoint 1  -- blind append, NO Bloom (urcu_txn_declare_disjoint)
  ryw1 : --disjoint 0  -- the default read-your-own-writes: Bloom + blind append

  -> disj BEATS the default ryw at every core count EXCEPT 64 (-3.5%): +5% to
     +17%.  Because both blind-append at age 0, the win is PURELY shedding the
     Bloom: at 1-32 cores the filter is maintained for nothing (0 true WAW, 0
     aborts on disj), and at 128-192 cores it also sheds the filter's
     now-counterproductive false-positive escalations -- the default carries the
     most aborts there (3.06M vs disj 2.55M at 192c).
  -> The 64c dip is the one place the Bloom's interleaved, data-dependent RMW
     buys a small microarchitectural throttle at that contention resonance: there
     the default aborts LESS than disj (1.10M vs 1.64M).  Real but unharvestable
     by a plain spin, and a net loss everywhere else.

WHY THE DEFAULT-RYW 64c EDGE IS NOT ADMISSION CONTROL
  With the 1024-bit k=3 filter the within-commit false-positive rate is ~1e-4 per
  slot, so <0.4% of commits escalate, and the write set has 0 true WAW -- so the
  Bloom resolves nothing real here.  Its only effect on throughput is the
  per-attempt RMW cost (a net loss at 1-32 and 128-192 cores) minus, at 64 cores
  alone, a microarchitectural throttle its jittered RMW incidentally applies at
  that resonance.  A plain spin cannot reproduce the 64c edge; the disjoint hint
  captures the honest half -- the filter cost removed -- everywhere.

CORRECTNESS
  Conservation passes at every core count with --disjoint 1 (all owned keys
  accounted, 100% reader hit).  -DURCU_TXN_DEBUG_DISJOINT run on the aliasing
  config (movesper 4, nbuckets 2, --disjoint 1) traps immediately with a
  diagnostic (SIGABRT), confirming the contract check catches a mis-declared
  handle; the same build on the disjoint config runs clean.  The default engine
  now auto-declares disjoint when a commit's keys cannot share a bucket
  (span <= nbuckets), so the shipped 3-hash config takes this fast path; an
  aliasing config falls back to the default read-your-own-writes.  Engine unit
  tests stay green.
